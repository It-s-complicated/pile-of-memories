# Svelte state sharing for the board

Researched 2026-10-13 against current official Svelte/SvelteKit documentation. The installed project uses Svelte 5.57.2 and SvelteKit 3.0.1. The recommendations below are architectural judgments for this repository, separate from framework behavior.

## What the current code needs

[BoardTools.svelte](src/components/BoardTools.svelte) receives six state values and six action callbacks directly from [App.svelte](src/App.svelte). This is a wide component interface; there are no intervening components forwarding those twelve props. Svelte describes prop drilling as passing values through intermediate component layers. [Context documentation](https://svelte.dev/docs/svelte/context).

There is a concrete forwarding path for account controls: `+page.svelte` supplies `signingOut` and `onsignout` to `App`, which forwards them to `BoardTools`. Most of the other dialog connections are direct parent-child interfaces.

The existing [card-persistence.ts](src/lib/card-persistence.ts) context serves a stronger case: `App` supplies persistence commands and a live `browse` getter function; [MemoryNode.svelte](src/components/MemoryNode.svelte) consumes them through Svelte Flow's component tree. Its `$derived(cardPersistence.browse())` reads the current mode rather than an initialization snapshot.

## Framework guidance

- **Props and callbacks:** Props update when their parent values change. Svelte recommends callbacks for communicating changes, or `$bindable` when parent and child deliberately share a value. Children should avoid mutating ordinary props, especially another component's reactive object. Explicit typed props remain useful for reusable components and dependencies visible at the call site. [Props](https://svelte.dev/docs/svelte/$props).
- **Typed context:** Svelte recommends `createContext<T>()` over manually keyed `setContext`/`getContext`; it has been available since 5.40. Context reaches descendants and is scoped to their component tree. Register and retrieve context during component initialization; event handlers should use the already retrieved object. A missing provider causes the generated getter to throw. [Context](https://svelte.dev/docs/svelte/context), [API reference](https://svelte.dev/docs/svelte/svelte#createContext), [context lifecycle](https://svelte.dev/docs/svelte/svelte#setContext).
- **Reactive context:** Context does not automatically make an ordinary value reactive. Passing a primitive directly captures its current value. Use a function or object getter that reads the current state, or provide a stable `$state` object and update its properties. Replacing that provided object breaks existing consumers' references. Reading reactive fields into ordinary destructured variables also captures values; retain property access or derive the values. [State boundaries](https://svelte.dev/docs/svelte/$state#Passing-state-into-functions), [context with state](https://svelte.dev/docs/svelte/context#Using-context-with-state).
- **Reactive modules:** `.svelte.ts`/`.svelte.js` modules support runes for reusable logic outside components. A factory or class can own state and actions; context or props can then distribute its instance. These mechanisms complement one another. Directly exporting state that is reassigned is unsupported; expose getter functions, a stable object, or reactive class fields instead. Class methods used as callbacks must preserve `this`, for example with arrow methods. [Reactive modules](https://svelte.dev/docs/svelte/svelte-js-files), [module state and classes](https://svelte.dev/docs/svelte/$state).
- **Composition:** Snippets can reference their surrounding component's state and be passed as content props. A shell can own layout/popover behavior while its parent supplies controls that already access parent state. This can avoid passing each control's data through the shell. [Snippets](https://svelte.dev/docs/svelte/snippet).
- **Bindings and stores:** `$bindable` is an explicit two-way contract, useful for inputs; Svelte cautions against frequent use. Stores remain supported and useful for complex asynchronous streams or explicit subscription/update control. Runes have reduced the need for stores merely to share ordinary state or extract logic. [Bindable props](https://svelte.dev/docs/svelte/$bindable), [when to use stores](https://svelte.dev/docs/svelte/stores#When-to-use-stores).

## Recommendation for this repository

My recommendation is a small typed board-controls context provided by `App`, following the existing card-persistence pattern. `BoardTools` is already specific to this board, and related board controls use the same mode and layout lifecycle. Expose live read access and named commands rather than every internal variable. Keep popover DOM behavior inside `BoardTools` and keep card persistence as its separate capability. A context consumer requires a provider when rendered in isolation, unlike the current prop-driven component.

Keep explicit props for small reusable components such as `BoardNotice`, `TagEditor`, `MemoryMarkdown`, and the two-prop `CaptureButton`. Compact dialog interfaces can also remain explicit; prop count alone does not justify context. A page-scoped account context could remove the account forwarding path while leaving sign-out orchestration with its current owner.

For a genuinely reusable tools component, two cohesive typed props (a state view and commands) are another option. Build the changing state view with `$derived` or live getters; do not construct a plain object once from current booleans. Grouping improves readability but does not reduce the toolbar's actual dependencies.

Extract a per-board controller into `.svelte.ts` when cohesive behavior warrants it; changing how twelve props travel alone does not justify moving cache, dialogs, viewport, and reorganization together. Snippet composition is useful if a reusable popover shell becomes the desired boundary. Neither `$bindable` nor a new store is needed for toolbar commands such as opening dialogs or toggling a persisted mode.

[The root layout](src/routes/+layout.ts) currently disables SSR, so this research does not establish a current cross-request state leak. Nevertheless, prefer creating state per board instance: it follows the current user-keyed `App` lifecycle and keeps future multiple boards or account changes isolated. If SSR is enabled later, mutable module singletons can share user data across requests; context avoids that scope. [SvelteKit state management](https://svelte.dev/docs/kit/state-management), [Svelte best practices](https://svelte.dev/docs/svelte/best-practices#Context).
